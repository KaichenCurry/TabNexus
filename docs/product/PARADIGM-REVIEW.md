## 总评：**方向认可（8/10），但有 4 处必须修正，2 处事实错误**

### 一句话结论

> **这个范式比我的"渐进式清理"更对。我改的是"界面怎么摆"，它改的是"这个产品到底是什么"——后者才是你说的"混乱"的真正根源。**
>
> 但它对代码现实的判断有硬伤，"推倒重来"这个措辞会把你带进一个不必要的高风险区。**正确的说法是：换外壳、保引擎、砍两个功能。**

## 第一部分 · 认可什么（这是真洞察）

### ✅ 1. 「文档」比「看板」更接近你的真实理念

你最初那句话是："很多文档、HTML 都是通过浏览器打开的。"

我上一轮把它翻译成**「文件系统」**（Tab=文件，Workspace=文件夹）。
它翻译成**「你正在写的那张纸」**（Tab=引用，Workspace=文档）。

**它的翻译更好。** 原因：

| | 文件系统隐喻 | 文档隐喻 |
|---|---|---|
| 终点 | 存好了（还是收纳） | **写完了**（有交付物） |
| 解决坟场问题 | ❌ 文件夹天然会被遗忘 | ✅ 未完成的文档会催你回来 |
| 导出的地位 | 一个功能 | **所见即所得，不存在"导出"** |
| Agent 的角色 | 读取者 | **共同编辑者** |

**最关键的一点**：文件夹是**静态容器**，文档是**未完成状态**。人会遗忘文件夹，但会惦记没写完的东西。**这直接命中 P3（收不拢）和 7 日回访率。**

### ✅ 2. "导出是降级方案"这个矛盾被彻底消解

我之前指出"主 CTA 是导出，但导出是 P2 的降级方案"——这是个**修补式**的批评，我给的方案是"把导出降级、把交给 Agent 提上来"。

它的方案更彻底：**文档本身就是交付物，不存在导出这个动作。** 这比我的修补高明。

### ✅ 3. 五个固定角色节是正确的取舍

我建议"角色骨架替代域名分组"，但仍保留用户自建分组。它主张**完全固定**。

**它是对的，理由有三：**
1. 用户不必学"建分组"这个概念（少一个名词）
2. **AI 归位准确率大幅提升**——从开放式聚类（难）变成五选一分类（易）。这直接解决你 PRD §5 里最大的风险："聚类不准"
3. 文档天然有叙事结构：背景→证据→反例→结论

> 补充一个它没说的理由：**固定角色让 MCP 契约变得稳定。** Agent 面对"五个固定角色"比面对"用户任意命名的分组"好写得多。这对 DSH 生态是加分项。

### ✅ 4. 「归位」统一动词、单视图无切换、收件口 1 按钮

这三条和我的结论一致，不再赘述。

## 第二部分 · 两处事实错误（必须纠正）

### ❌ 错误 1：「189 项测试保住」

原文："旧数据 1:1 迁移，MCP 契约不动——**189 项测试**和 Agent 兼容性保住。"

**实测：`tests/` 目录 `it(`/`test(` 定义共 123 处**（189 出自 `IMPLEMENTATION_STATUS.md`，含参数化展开与 E2E 场景计数，无法在源码中直接复现）。

更重要的是——**测试根本保不住**，见下表：

| 测试文件 | 用例数 | 换外壳后 |
|---|:--:|---|
| `workspace-ui.test.tsx` | **17** | 🔴 **全部作废**（测的是看板 UI） |
| `structure.test.ts` | 3 | 🔴 关系图相关，砍掉即作废 |
| `grouping.test.ts` | 5 | ⚠️ 需重写（域名分组→角色归位） |
| `collaboration.test.ts` | 10 | ✅ 保留 |
| `background.test.ts` | 10 | ✅ 保留 |
| `storage.test.ts` | 8 | ✅ 保留 |
| 其余 | ~70 | ✅ 大部分保留 |

**真实情况：约 25 个用例需要重写，98 个保留。** 这个成本不大，但方案里说"保住"是不准确的，会低估工作量。

### ❌ 错误 2：「MCP 契约不动」

这条是**错的**，而且是这份方案里风险最高的地方。

实测 17 个 MCP 工具中，**有 3 个与被砍掉的关系图直接绑定**：

```
propose_structure     ← 整个工具就是关系图提案（"relationship proposal"）
edit_workspace        ← 操作枚举含 upsert_edges / remove_edges / position_cards / reset_card_positions
read_workspace        ← 返回体含 edges 字段（collaboration.ts:424, 472, 490）
```

**砍掉关系图 = MCP 契约必然变更。** 后果：

- 已适配的 Codex / Cursor / Claude / VS Code / TRAE 五个客户端行为改变
- `docs/MCP_CAPABILITY_MATRIX.md` 需更新
- 若已有用户在用，是 **breaking change**

> 这不是不能做，而是**必须明确规划**，不能用"契约不动"一句话带过。见下面我的修正建议。

## 第三部分 · 四处必须修正

### 🔧 修正 1：关系图——不要砍，要「降维」（这是我和它最大的分歧）

**它的建议**：彻底砍掉，v2 再议。

**我的判断：砍掉数据层是错的，砍掉画布是对的。**

区分两件事：

| | 建议 |
|---|---|
| **FlowCanvas 画布 UI**（503 行，手动连线） | ✅ **砍**。要求用户手动连线，成本极高、几乎没人付，且与文档范式冲突 |
| **`edges` 数据结构 + `propose_structure` 工具** | 🔴 **保留**。砍了会破坏 MCP 契约，且丢掉一个未来的核心能力 |

**保留 edges 的三个理由：**

1. **它是 MCP 契约的一部分**，砍了就是 breaking change（见上）
2. **文档范式反而更需要引用关系**：论文里的"引用"、"反驳"、"支撑"——这正是文档的原生概念，不是看板的
3. **这是 P3（收不拢）的未来杀手锏**：AI 检测"3 个证据都支持同一结论，没有反例" → 这个"结构缺口提示"能力依赖 edges

**具体做法**：
- 删掉 `FlowCanvas.tsx`（画布）和视图切换
- `edges` 保留在数据模型和 MCP 中
- 在文档条目上做一个**极轻的角标**：`↳ 反驳了「XX」`，点击跳转
- `propose_structure` 工具保留，但结果不再画图，而是**在文档里以角标 + 缺口提示呈现**

> 一句话：**砍掉"画关系图"这个交互，保留"知道关系"这个能力。**

### 🔧 修正 2：五个角色节不够——必须加第六个「已排除」

这是我上一轮论证的核心，方案里漏了。

原文的五节：背景 / 证据 / 反例 / 方案 / 结论。

**必须加第六节：`已排除`（Excluded）。**

理由（这是你对 Browser Use 的**唯一不可复制优势**）：

> Browser Use 能读你现在开着的 30 个 Tab。但其中 8 个是你看完判断"此路不通"的——它会平等对待，甚至因为内容详实给更高权重，得出你三天前就否决掉的结论。
> **你的否决决定不存在于任何页面里。**

在文档范式下，这一节甚至更自然——**任何严肃的研究文档都有"已排除方案及原因"这一章。**

数据层：
```ts
role: "excluded";
excludedReason: string;   // "数据过期，产品已重构"
```

导出给 Agent 时：
```markdown
## 已排除（不要基于这些下结论）
- [某篇 2023 年旧测评] — 排除原因：数据过期，产品已重构
```

> ⚠️ **注意**：「反例」≠「已排除」。反例是**有效的反面证据**（要纳入结论），已排除是**无效素材**（不要纳入）。两者性质相反，必须分开。

**所以是 6 个角色节**，且 `已排除` 默认折叠（不占视觉），只在导出和 Agent 读取时完整传递。

### 🔧 修正 3：「推倒重来」措辞危险——正确表述是「换外壳」

原文说"不修、不改、不继承——推倒重来"，但方案后半段自己又说"引擎复用、数据模型零破坏"。**这两句是矛盾的。**

实际改动范围（源码实测 10,143 行）：

| 层 | 文件 | 行数 | 处置 |
|---|---|---:|---|
| **UI 外壳** | `WorkspaceApp.tsx` | 1,316 | 🔴 重写 |
| | `FlowCanvas.tsx` | 503 | 🔴 删除 |
| | `GroupPanel.tsx` | 115 | 🔴 重写为角色节 |
| | `CardRow.tsx` | — | 🔄 重写为引用条目 |
| | `OpenTabsRail.tsx` | 361 | 🔄 简化为收件口 |
| **引擎** | `collaboration.ts` | 877 | ✅ 保留（微调 edges 呈现） |
| | `storage.ts` / `workspace.ts` | 641 | ✅ 保留 |
| | `background.ts` / `agent.ts` / `aiProviders.ts` 等 | ~2,000 | ✅ 保留 |
| | `grouping.ts` | 145 | 🔄 改为角色归位 |

**约 2,300 行重写 / 500 行删除 / 7,300 行保留。即：22% 重写，72% 不动。**

> 这是一次**大重构**，不是**重写**。用词准确很重要——因为"推倒重来"会诱导你去动那 72%，那才是真正的风险。

### 🔧 修正 4：DSH 优先级被降到了 R4（应该并行前置）

原文把 DSH 排在 R4，虽注明"可与 R1 并行"，但排序上给了错误信号。

**DSH Layer 1（MCP 直连）应该是 R0，1–2 天完成，先于所有 UI 工作。**

理由：
- 生态第 3 天，窗口以周计（UI 重构要 4–6 周，等不起）
- 与 UI 改动**零耦合**（MCP 层不动）
- 命中的是护城河层（L3），而 UI 重构改善的是 L1/L2

> 而且有个战术好处：**DSH 插件先发出去，能给你真实的 Agent 侧反馈**，反过来验证角色节设计对不对。

## 第四部分 · 三个拍板问题，我的答复

### Q1：关系图彻底砍掉，舍得吗？

**答：砍画布，留数据和工具。**（见修正 1）

- 删 `FlowCanvas.tsx` + 视图切换 → ✅ 同意，这个交互没人用
- 删 `edges` + `propose_structure` → ❌ 反对，会破坏 MCP 契约并丢掉"缺口检测"这个 P3 杀手锏
- 折中：关系以**条目角标**呈现（`↳ 反驳了「XX」`），零画布成本

### Q2：五个固定角色，不允许自建，接受吗？

**答：接受"固定"，但必须是六个（加「已排除」），且要留一个后门。**

- 固定角色 ✅ 强烈支持（AI 准确率 + 界面简洁的关键取舍）
- 五个 → **六个**（加 `已排除`，见修正 2）
- **后门**：允许角色节内部有轻量子标签（用户自由打 tag），满足极少数复杂场景，但不影响主结构

> 为什么要后门：完全禁止自定义，会在某些场景（比如按"竞品 A / 竞品 B"组织）逼用户放弃产品。子标签是零成本的泄压阀。

### Q3：结论节形态？

**答：同意"最薄"，但补两点。**

- 一句话结论 + 纯文本区，不引入富文本 ✅ 完全同意
- **补 1**：结论节要有**证据锚点**——写结论时可 `@` 引用上面的条目，生成 `依据：证据#3、反例#1`。这是文档范式相对看板的**核心增值**，成本极低（就是个引用 chip）
- **补 2**：结论写完后，任务状态变为**「已交付」**，从活跃列表移入归档区。**这是 P3 的闭环信号，也是"7 日回访率"之外最该测的指标**

### 分期（修正后）

| 期 | 内容 | 工期 | 依赖 |
|:--:|---|:--:|---|

### 数据层改动（一次做完，避免反复迁移）

```ts
export type CardRole =
  | "background" | "evidence" | "counter"
  | "option" | "conclusion" | "excluded";

export type Card = {
  // ...现有字段全部保留
  role?: CardRole;
  excludedReason?: string;
  tags?: string[];          // 角色节内子标签（泄压阀）
};

export type Workspace = {
  // ...现有字段全部保留
  intent?: string;
  nextStep?: string;
  conclusion?: string;
  conclusionRefs?: string[];  // 证据锚点：引用的 cardId
  deliveredAt?: string;       // 已交付时间（P3 度量）
};
```

**全部 optional，旧数据无需迁移，`SCHEMA_VERSION` 保持 1。**

### MCP 契约变更（必须明确规划，不能说"不动"）

| 工具 | 变更 | 兼容策略 |
|---|---|---|
| `read_workspace` | 返回体加 `role`/`intent`/`conclusion` | 加字段，向后兼容 ✅ |
| `edit_workspace` | 操作枚举加 `set_role`；`upsert_edges` 保留 | 加操作，兼容 ✅ |
| `propose_structure` | 保留，语义从"画布布局"改为"关系+缺口" | 语义微调 ⚠️ 需更新文档 |
| `add_card` | 支持传 `role` | 加可选参数 ✅ |
| 涉及 `position_cards`/`reset_card_positions` | 画布删除后成为 no-op | 🔴 **标记 deprecated，保留一个版本再移除** |

> 这样处理，五个已适配客户端**不会立刻挂**，给你一个平滑过渡期。

## 结论

| 项 | 判定 |
|---|---|
| **范式方向（文档 > 看板）** | ✅ **认可，比我上一轮的方案更对** |
| **固定角色节** | ✅ 认可，但**必须六个**（加「已排除」） |
| **砍关系图** | ⚠️ **部分反对**：砍画布可以，砍 `edges`/`propose_structure` 会破坏 MCP 契约 |
