## 0. 结论先行

你的产品**理念是对的，实现也基本做完了，混乱出在"表达层"**：一个正确的内核（Tab = 任务上下文）被包在一套仍然按"标签管理器"组织的界面和名词体系里。

三句话概括：

1. **定位**：TabNexus 不是 Tab Manager，是**浏览器里的任务文件系统**——把散落的 Tab 变成一件事的"文件页"，人能接着做，Agent 能直接读。
2. **三大问题**：上下文**记不住**（Why 丢失）→ 上下文**传不走**（人肉 API）→ 上下文**收不拢**（保存即遗忘）。
3. **界面主症结**：缺一个叫「任务」的一级对象；左右两套并行的管理台；卡片上显示的是"页面来自哪里"（域名），而不是"它在这件事里是什么"（角色）。

---

## 1. 现状诊断：混乱到底在哪

### 1.1 概念层：名词太多，且缺一个一级对象

现在界面上并列出现的名词：工作区、分组、卡片、资料、待整理、标签操作台、当前窗口、Agent 活动、结构建议、关系图、本地模式、阅读状态、资料类型……**11+ 个概念，用户第一次打开无法建立心智模型。**

更关键的是：**没有「任务」这个对象。**

你的全部叙事都建立在"这 30 个 Tab 是一件事的上下文"上，但界面里那件"事"只是左侧栏一行叫「我的工作区」的文字。它没有：

- 目标（我要得出什么结论）
- 进度（这件事做到哪了）
- 下一步（回来先干什么）
- 产出（结论存在哪）

**结果**：Workspace 事实上退化成了"文件夹"，和 Toby 的 Collection 没有本质区别——你在 README 里批判的东西，正是当前 UI 的默认形态。

### 1.2 界面层：三个具体问题

**（a）左右两套并行的管理台，同一批对象说两种话**

截图里，中间是「分组看板」（卡片：待读 / 浏览器中打开 / WEB），右侧是「标签操作台」（标签：已保存 / 未保存 / 固定 / 保存·本地整理·关闭·重开）。

同一个网页，在左边叫"卡片"、有一套状态，在右边叫"标签"、有另一套状态。用户必须同时维护两个心智模型，还要自己在脑子里做映射。**右侧不该是第二个管理台，它只该是一个"入口"。**

**（b）顶部工具栏 8 个按钮全部平级**

`分组看板 | 关系图 | 添加资料 | 新建分组 | AI 助手 | Agent 活动 | 导出 | 撤销 AI 整理`

视图切换、内容创建、AI 能力、协作、输出——五种性质的操作挤在一行，没有主次。用户看不出"我现在最该点哪个"。而且唯一被高亮成实心主按钮的是**「导出」**，等于在告诉用户"这个产品的主行动是导出"。

**（c）卡片显示的是域名，不是角色**

卡片当前信息：标题 / 域名 / 待读 / 浏览器中打开 / WEB。分组名是 `crunchbase.com`、`research.test`、`design.test`。

这正好是你自己写的那句批判：*"按域名整理只能告诉你'页面来自哪里'，却不知道'你为什么打开它'。"* 但**默认体验（本地模式）就是域名分组**，而 AI 分组要用户先去设置里配 Key。**产品最有说服力的那一面，被放在了付费/配置门槛之后，默认呈现的恰恰是自己批判的形态。**

备注（note）字段、卡片角色、任务进度这些真正的差异化信息，在卡片上完全看不见。

### 1.3 叙事层：README 和产品是两个东西

README 写得很好（"你开的不是标签页，是一件还没做完的事"），但打开产品看到的是：一个空的分组看板 + 一句"从右侧勾选标签并点击 AI 整理"。**叙事讲的是任务，产品教的是整理标签。** 用户的第一次体验没有兑现承诺。

## 2. 核心理念定稿：Tab = 任务的文件页

你说的关键判断是对的，这里把它固化成可以指导所有设计决策的一句话：

> **浏览器已经变成新的操作系统，Tab 已经变成新的文件页——但浏览器从来没有给它配一个文件系统。TabNexus 就是那个文件系统。**

这个比喻能立住，是因为它在 AI 时代有实感：飞书文档、语雀、Notion、AI 生成的 HTML 报告、Figma、GitHub PR——**它们全都没有本地文件，只有一个 Tab。** 用户桌面上的 `~/Documents` 是空的，真正的工作文件全在标签栏里，而标签栏没有目录、没有命名、没有版本、没有 API。

### 映射表（用这张表统一所有命名和设计）

| 传统文件系统 | 浏览器现状 | TabNexus |
|---|---|---|
| 文件 | Tab（只有 URL） | **Card** — 带角色、备注、状态的文件页 |
| 文件夹 | 无（只有窗口） | **Task Workspace** — 一件事的现场 |
| 文件名/类型 | 网页标题 | **角色**：背景 / 证据 / 反例 / 方案 / 结论 |
| 打开记录 | 历史记录（时间流） | **进度**：待读 / 已读 / 已采用 |
| 引用关系 | 无 | **关系图**：支持 / 反驳 / 依赖 / 下一步 |
| 文件系统 API | 无（只能截图/爬） | **MCP 17 工具** — Agent 直接读写 |
| 产出文件 | 另存为 | **Report Card** — 结论写回同一个 Workspace |

**这张表就是你的护城河说明书**：竞品做到第 1、2 行；你做到第 7 行。

### 对外一句话（三种长度）

- **7 字**：浏览器的任务文件系统
- **一句**：TabNexus 把浏览器里散落的 Tab，变成人和 AI 都能接着用的任务上下文。
- **一段**：AI 时代你的文件不在硬盘里，在标签栏里。TabNexus 给这些 Tab 补上文件系统缺的那一层：它们属于哪件事、扮演什么角色、做到了哪一步；然后通过 MCP 把这份上下文整份交给 Agent，不用再逐条复制链接。

## 3. 产品定位：解决哪三大问题

三个问题不是三个功能，是**同一份上下文的三段生命周期**：记得住 → 传得走 → 收得拢。任何新需求，如果不落在这三段里，就不做。

### P1 · 上下文记不住：Tab 只存了 URL，没存"为什么"

**痛点场景**：调研一家公司开了 28 个 Tab。第二天回来，页面都在，但"哪几个是核心证据、哪个和哪个矛盾、我看到第几个了"全没了。于是你不敢关，只能让它一直开着——**用"开着不关"当备忘录。**

**现有方案为什么不行**：Toby / OneTab / Workona 存的是 URL + 标题 + 文件夹名。恢复的是"一组网页"，不是"上次思考到一半的现场"。

**TabNexus 怎么解**：
- 每张卡片带**角色**（背景/证据/反例/方案/结论）+ 备注 + 阅读状态
- Workspace 带**任务目标**和**下一步**
- 恢复时，恢复的是判断结构，不是浏览器窗口

**衡量**：Workspace 7 日回访率 ≥ 40%（你 PRD 里的北极星，保留）

---

### P2 · 上下文传不走：你在当浏览器和 AI 之间的人肉 API

**痛点场景（这是 AI 时代的新增量，也是你最强的一条）**：调研做完了，你想让 Codex/Cursor/Claude 帮你写报告。于是你开始逐条复制 20 个链接、重新打字解释"这个是竞品定价、那个是他们的技术博客、这篇观点和前面那篇矛盾"。**你花在"喂上下文"上的时间，超过了做调研本身。**

替代方案更糟：让 Computer Use / Playwright 逐页重新读取——慢、贵、还会读错。

**现有方案为什么不行**：Toby 的终点是人看的看板，Agent 拿不到。

> ⚠️ **重要更正（2026-08-15 竞品核实后）**
> 我上一版写的"没有竞品把浏览器上下文做成 Agent 可读接口"是**错的**。实测检索发现这个赛道已经很拥挤：
> - **mcp-chrome**（hangwin，GitHub 12.3k stars，MIT）：Chrome 扩展式 MCP Server，20+ 工具，含 `get_windows_and_tabs`、跨 Tab 语义搜索、内置向量库
> - **Browser MCP**、**browser-control-mcp**（Firefox）、**Chrome DevTools MCP**（Google 官方）：都能让 Agent 读取和操作标签
> - **WebMCP**：Chrome 149 已进入 origin trial，配合 Gemini in Chrome、auto browse、Skills in Chrome——**Google 正在把"Agent 读浏览器"变成浏览器原生能力**
>
> 所以"Agent 能读我的标签"**已经不是差异化了，正在变成基础设施。**

**但这恰恰让 TabNexus 的差异化更清楚了**，只要说对一件事：

| | 现有 Browser MCP / WebMCP | TabNexus |
|---|---|---|
| 读的是什么 | **当前开着的 Tab**（实时快照） | **一件事的完整上下文**（含已关闭的页） |
| 生命周期 | Tab 关了，上下文就没了 | Tab 关了，上下文还在（**这是核心**） |
| 内容 | URL + 标题 + 页面正文 | URL + **人的判断**：角色、备注、关系、进度 |
| 谁做的整理 | 无（Agent 自己猜 30 个 Tab 的关系） | 人 + AI 已经整理好，Agent 直接用 |
| 隐私 | 常需读全文、注入脚本 | 只传元数据，不读正文 |

一句话：**它们让 Agent "看见"你的浏览器；TabNexus 让 Agent "接手"你的任务。**

WebMCP 那篇分析里有一句话正好是你的机会：*"如果工具只在页面打开时存在，用户的开启标签集就成了 Agent 运行时的一部分……缺失的那一层是 cross-tab inventory（跨标签清单）。"* ——**你做的就是那一层，而且是带人类判断的持久化版本。**

**TabNexus 怎么解**：
- 本地 MCP（17 工具）：Agent 一次读到分组、备注、角色、关系、进度
- **持久化**：读的是 Workspace 不是 live tabs，页面关了上下文仍在
- **双向**：Agent 能补资料、更新状态、写回报告——上下文越用越厚，而不是被消费掉
- 破坏性操作需人确认；只监听 127.0.0.1；不读网页正文

**衡量**：周均"交给 Agent"次数 ≥ 2；对照实验中结构化上下文 vs 平铺 URL 的来回轮次减少

> ⚠️ **这仍是你的长期护城河，但护城河的位置要挪一格。**
> 不是"能不能让 Agent 读浏览器"（这一格已被 mcp-chrome / WebMCP 占了，且 Google 会免费送），
> 而是"**Agent 读到的是一堆 Tab，还是一份已经被人判断过的任务上下文**"。
> 前者是管道，会被平台收编；后者是**沉淀的用户资产**，平台做不了——因为它需要用户长期投入的备注和判断。
> **产品资源应向 P2 倾斜，但叙事必须强调"持久化 + 人的判断"，而不是"我们支持 MCP"。**

---

### P3 · 上下文收不拢：存起来了，然后就没有然后了

**痛点场景**：你开 30 个 Tab 不是为了收藏 30 个网页，是为了得出**一个结论**。但所有工具的终点都是"存好了"。存完之后，这个 Collection 就进了坟场，再也不打开。

**现有方案为什么不行**："保存即遗忘"是这个品类的共同宿命——因为保存的东西和产出的东西是两个地方（Toby 里存链接，Notion 里写结论），保存物很快就与真实工作脱节。

**TabNexus 怎么解**：
- 任务有**终点态**：Workspace 里能直接产出结论卡片 / 报告，产出物和素材在同一份上下文里
- 进度可见：这件事推进了多少、还缺什么证据
- 关系图不是画着好看，是用来发现"这里还缺一个反例"

**衡量**：产生了结论/报告卡片的 Workspace 占比 ≥ 30%

---

### 明确不解决（写进 PRD，用来挡需求）

- ❌ 不做书签管理器 / 稍后读（Pocket、Raindrop 的活）
- ❌ 不做团队协作和云同步（本地优先是信任前提）
- ❌ 不做网页正文抓取和全文搜索（隐私边界 + 不是核心）
- ❌ 不做新标签页劫持
- ❌ 不做通用笔记（Notion 的活）——笔记只作为任务产出物存在

## 4. 由三大问题倒推的功能地图

把现有已实现功能重新分档。**当前的问题不是功能少，是所有功能被摆成了平级。**

| 功能 | 归属 | 定位 | 处置 |
|---|---|---|---|
| 采集/保存/恢复 Tab | P1 | 地基（不是卖点） | **降为后台能力**，别占据 UI 主位 |
| 卡片角色 + 备注 | P1 | **核心差异化** | **提到卡片正面**，现在几乎看不见 |
| 任务目标 + 下一步 | P1 | **缺失，必须补** | P0 新增 |
| 阅读进度三态 | P1 | 支撑 | 保留，弱化视觉 |
| MCP 17 工具 | **P2** | **护城河** | **提到一级入口**，现在藏在设置里 |
| Agent 活动记录 | P2 | 信任机制 | 保留，合并进任务时间线 |
| Markdown/JSON 导出 | P2 | MCP 的降级方案 | **从主按钮降级**为二级菜单 |
| AI 意图分组 | 加速器 | 降低整理成本 | 保留，但**不能是价值前提** |
| 关系图 | P3 | 高潜力但成本高 | **改为 AI 生成为主、手动为辅** |
| 结论/报告产出 | **P3** | **缺失，必须补** | P0 新增 |
| 多 Workspace | 地基 | — | 保留 |
| 域名分组（本地模式） | — | **反定位** | **改为兜底**，不做默认展示形态 |

**一句话**：你已经把 P1 做到 100 分、P2 做到 80 分（但没人看得见）、P3 做到 20 分。而界面把 60% 的面积给了 P1 的地基部分。

## 5. 界面重构方案

### 5.1 先砍名词：11 个 → 5 个

| 保留（一级） | 含义 | 砍掉/合并 |
|---|---|---|
| **任务（Task）** | 原 Workspace，一件事 | — |
| **页（Page）** | 原卡片/资料，统一叫法 | "卡片"、"资料"二选一，别混用 |
| **角色（Role）** | 背景/证据/反例/方案/结论 | 替代"资料类型 WEB" |
| **进度（Status）** | 待读/已读/已采用 | 合并"阅读状态" |
| **收件口（Inbox）** | 原"标签操作台"+"待整理" | 两者合并 |

「本地模式」「结构建议」「Agent 活动」「当前窗口」全部降为二级，不出现在主界面标签上。

### 5.2 布局：从"双管理台"改为"一条任务流"

```
┌──────────┬────────────────────────────────────────┬─────────────┐
│ 任务列表  │  ① 任务头（新增·最重要）                 │  收件口      │
│          │  🎯 目标：评估 Perplexity 的商业模式      │  （原操作台） │
│ ● 竞品调研│  ▓▓▓▓▓▓░░░░ 12/18 已读 · 3 已采用        │             │
│   28 页  │  ⏭ 下一步：补一个反面案例                 │  当前窗口 12 │
│ ○ 官网改版│  ──────────────────────────────────    │  ┌─────────┐│
│   9 页   │  ② 看板 / 关系图（同一份数据）            │  │未归位 3 ↓││
│ ○ Bug排查│                                        │  └─────────┘│
│   6 页   │   [证据]   [反例]   [方案]   [结论]      │  已在任务中 9│
│          │    4页      1页      3页    ⬜ 待产出     │  （灰显）    │
│ ＋新任务  │                                        │             │
│          │  ③ 底部条：▶ 交给 Agent 继续              │             │
└──────────┴────────────────────────────────────────┴─────────────┘
```

**四个关键改动：**

**① 加"任务头"（P0，最高优先级）**
主区顶部固定一条：目标一句话 + 进度条 + 下一步。这一条把 Workspace 从"文件夹"变成"任务"，是整个重构里 ROI 最高的一步。目标可以在保存第一批 Tab 时由 AI 从标题里猜一句，用户改。

**② 右侧从"管理台"降级为"收件口"**
右侧只回答一个问题：**当前窗口里，哪些还没归位。** 已保存的默认折叠/灰显，不再提供"关闭/重开/本地整理"这套并行操作——那些操作属于主区。右侧只留：勾选 → 一个按钮「收进任务」。
> 现在右侧有 6 个按钮（保存/本地整理/关闭/重开/全选/展开），比主区还复杂，这是本末倒置。

**③ 分组默认按角色，不按域名**
无 API Key 时也不要显示 `crunchbase.com` 作为分组名。用本地规则先给出**空的角色骨架**（背景 / 证据 / 待定），让用户拖——哪怕手动，也比域名分组更贴合定位。域名分组保留为"其他排序方式"里的一个选项。

**④ 主 CTA 从「导出」换成「交给 Agent 继续」**
现在唯一的实心按钮是"导出"，它是 P2 的降级方案却占了 C 位。换成 `▶ 交给 Agent 继续`（未配置时点击引导安装，配置后直接把上下文推给已连接的 Agent）。导出退到「…更多」里。

### 5.3 卡片重设计

```
现在：  标题
        crunchbase.com
        ● 待读   ● 浏览器中打开   WEB

改为：  ▎证据          ← 角色色条（一眼看出它在任务里是什么）
        Perplexity 融资轮次
        "估值 90 亿，但没披露 ARR" ← 备注上正面（关键！）
        crunchbase.com · 已读        ← 域名弱化为脚注
```

**核心原则**：卡片正面必须回答"**它在这件事里是什么**"，而不是"它来自哪个网站"。备注是用户投入的最高价值信息，现在被藏在二级菜单里，等于把差异化埋了。

### 5.4 关系图：从"画布"改为"缺口检查器"

现在的关系图要求用户手动连线——这个成本几乎没人会付。改变它的**目的**：

- 默认由 AI（或本地启发式）生成一张结构图，用户只做删改
- 图上高亮**结构缺口**："3 个证据都支持同一结论，没有反例" / "这两页结论矛盾"
- 这样关系图就从"装饰性可视化"变成 P3 的核心工具：帮你把上下文收敛成判断

### 5.5 首启：第一屏就要兑现叙事

当前空状态说的是"从右侧勾选标签并点击 AI 整理，分组会直接出现在这里"——这是在教工具操作。

改为：

> **这次你想搞清楚什么？**
> ［ 输入一句话，例如：评估 Perplexity 值不值得对标 ］
> 然后从右边把相关的页收进来。

先立"事"，再收"页"。**一句话的输入框，比任何 onboarding 教程都有效**，而且它顺手拿到了 AI 分组最需要的意图输入（现在 AI 分组要用户额外描述意图，很多人不会写）。

## 7.5 竞争格局（2026-08 核实）

三层竞争，你被夹在中间，但夹缝是真实存在的。

| 层 | 玩家 | 他们做什么 | 对 TabNexus 的威胁 | 你的应对 |
|---|---|---|---|---|
| **收纳层** | Toby、OneTab、Workona、Session Buddy、Tabox | 存 URL + 文件夹 | 低（同质化严重，且都停在"保存即遗忘"） | 不在这层竞争，L1 只做地基 |
| **AI 浏览器** | Dia、Comet、Atlas、Arc Max | 侧边栏 AI 读当前标签 | **中** — Comet 已能"跟踪你的进行中任务" | 他们要求换浏览器；你是 Chrome 扩展，迁移成本≈0。且据 2026-06 评测，Dia/Comet **都没有 Arc 式 workspace 体系**，标签组织仍是弱项 |
| **Agent 管道层** | mcp-chrome（12.3k★）、Browser MCP、Chrome DevTools MCP、**WebMCP（Chrome 149 origin trial）** | 让 Agent 读/控当前标签 | **高，且会被 Google 免费化** | **不比拼管道，比拼管道里流的东西**：他们送实时 Tab 快照，你送持久化的、带人类判断的任务上下文 |

**关键结论**：

1. **"支持 MCP"不能再当卖点写**。2026 年这已是标配，Google 甚至在把它做进浏览器内核。README 里"MCP 17 tools"的 badge 说明不了任何差异化。
2. **真正稀缺的是"关掉的 Tab 里的上下文"**。所有 Browser MCP 方案都只能读 live tabs——这是它们的架构上限，不是暂时的功能缺失。你的 Workspace 是持久化的，这是结构性差异。
3. **人的判断是唯一不可被平台复制的资产**。Google 能让 Gemini 读你 50 个 Tab，但它不知道你认为哪 3 个是关键证据、哪两个互相矛盾。这些标注是用户长期投入形成的，一旦积累就有迁移成本——**这才是护城河的真正来源**。
4. **叙事要改口径**：从"我们支持 Agent"改成"**别的工具让 Agent 看见你的浏览器，TabNexus 让 Agent 接手你的任务**"。

## 7.6 灵魂拷问：Browser Use / Computer Use 也能直接读所有 Tab 并总结，TabNexus 优势在哪？

**先承认对的部分**：是的，Browser Use / Computer Use / mcp-chrome 确实能读取当前所有 Tab 并做出像样的总结。**"读取 + 总结"这件事本身，TabNexus 没有优势，也不该假装有。**

但"能读"和"能接手任务"之间有六道结构性的坎。前三道是**架构上限**（他们做不到，不是暂时没做），后三道是**经济性问题**（他们能做，但不划算）。

### 🧱 架构上限：他们永远做不到的三件事

**① 时间维度：他们只能读"现在开着的"，读不到"昨天关掉的"**

这是最根本的一条。Browser Use 读的是 **live tabs 的实时快照**。

但真实任务不是一次性的。一个调研持续三天：第一天开了 30 个 Tab，关掉 20 个没用的，留下 10 个；第二天又开 15 个……到第三天让 Agent 总结时，**它看到的是当下那 12 个 Tab，而前两天那 45 个页面里的判断全部消失了**——包括你为什么关掉那 20 个。

Browser Use 没有"上周"这个概念。你的任务有。

> 这不是功能缺失，是架构决定的：只要上下文的载体是"浏览器进程里开着的 Tab"，它的生命周期就永远等于 Tab 的生命周期。**TabNexus 的载体是本地存储，生命周期等于任务的生命周期。**

**② 负信息：你"否决过什么"，是任何读取都恢复不了的**

假设你的 30 个 Tab 里，有 8 个是你看过之后判断"这条路走不通"的死胡同。

Browser Use 读到这 30 个页面，会**平等对待**它们——甚至可能因为那 8 个页面内容详实，反而在总结里给了更大权重，得出你三天前就已经否决掉的结论。

**你的否决决定，不存在于任何页面里，只存在于你脑子里。** 除非有工具把它记下来。这就是"角色 + 状态"字段的真正价值：它记录的不是页面内容，是**人对页面的判断**——包括正面的（这是核心证据）和负面的（这个已排除）。

> 一句话：**页面内容是公共的，Agent 自己能读；你对页面的判断是私有的，只有你能给。TabNexus 存的是后者。**

**③ 确定性：读取是概率性的，数据结构是确定性的**

Browser Use 每次读取的结果都不一样：懒加载没触发、需要滚动、弹了登录墙、Cookie 弹窗挡住、页面改版、内容是 JS 渲染的。同一个任务问两次，得到两份不同的总结。

TabNexus 读的是一份带 revision 的结构化数据——**同样的输入永远得到同样的输出**。对于"要拿来做决策"的工作流，这个差别是决定性的。

### 💰 经济性：他们能做但极不划算的三件事

**④ Token 成本：30 个 Tab 的正文，装不进上下文窗口**

这是个可以算的账：

| | Browser Use 读 30 个 Tab | TabNexus 交出同一份上下文 |
|---|---|---|
| 传输内容 | 每页正文（含导航、页脚、广告） | 标题 + 角色 + 备注 + 关系 + 状态 |
| 量级 | 单页 5k–50k tokens，30 页轻松突破上下文上限 | 全部 30 项约几 k tokens |
| 结果 | **实际只能读前几个 Tab，或每页先摘要再合并（多轮、慢、有损）** | 一次读完，无损 |
| 重复提问 | 每次重读一遍，成本线性叠加 | 读的是已沉淀的结果 |

所以"Browser Use 也能分析 30 个 Tab"这句话，在 5 个 Tab 时成立，在 30 个 Tab 时会退化成"读了前 6 个 + 猜"。而 **30 个 Tab 恰恰是 TabNexus 定义的核心场景**。

> 📌 **建议你把这个做成实测**：同一批 25 个真实 Tab，分别用 mcp-chrome / Browser Use 和 TabNexus 导出喂给同一个 Agent 做同一个任务，记录 token 数、耗时、来回轮次、结论质量。这正是你 PRD 里的 H2 假设，现在有了更强的对照组。**这个实验结果本身就是最好的 README 素材和最硬的融资/推广材料。**

**⑤ 隐私边界：读正文 vs 读元数据**

Browser Use 要总结就必须读页面正文——而你的 Tab 里有飞书文档、内网 Wiki、邮箱、CRM、财务后台。**"让 AI 读取我所有打开的页面"在很多公司是直接违规的。**

TabNexus 只传标题、URL、你写的备注和结构，**不发送网页正文**。这不只是隐私姿态，是能不能在企业环境里被允许安装的问题。你现有的隐私边界设计（不用 content script、不要 `<all_urls>`、只监听 127.0.0.1）本来就是对的，但**在 README 里被写成了"合规声明"，而不是"竞争优势"**。应该改口径。

**⑥ 单向 vs 双向：他们的产出流回聊天框就死了**

Browser Use 读完 → 输出一段总结到聊天窗口 → 你关掉窗口，它就没了。下次重来一遍。

TabNexus 里 Agent 的产出**写回同一个 Workspace**：补的资料、更新的状态、写的报告都留在任务里。**上下文是越用越厚的，不是每次被消费掉的。** 这是"记忆"和"查询"的区别。

### 🎯 战略结论：不要和 Browser Use 竞争，要做它的记忆层

这是这一节最重要的一句话：

> **Browser Use 是感知和执行层（读页面、点按钮），TabNexus 是记忆和判断层（这件事是什么、做到哪、谁被否决了）。它们不是竞品，是上下游。**

最强的形态不是"TabNexus 替代 Browser Use"，而是：

```
Agent 需要读某个页面的正文
        ↓
   调 Browser Use / mcp-chrome 去读  ← 他们擅长的
        ↓
   读完的结论、判断、角色标注
        ↓
   写回 TabNexus Workspace         ← 你擅长的
        ↓
   下次任何 Agent 接手，直接读到，不用重读
```

**建议**：不但不屏蔽 mcp-chrome / Browser MCP，反而在文档里明确说"**可以和它们配合使用**"。你不是第 6 个浏览器 MCP，你是它们缺的那块持久化存储。这个站位比硬碰硬安全得多，也真实得多。

### ⚖️ 诚实地说：什么时候 Browser Use 更好

写进文档，避免过度承诺（也让你的定位更可信）：

| 场景 | 赢家 |
|---|---|
| "总结我现在开着的这 5 个页面" | **Browser Use** — 零配置，即问即答 |
| 需要页面正文的深度阅读、翻译、提取表格 | **Browser Use** — TabNexus 不读正文 |
| 填表单、点按钮、跑自动化流程 | **Browser Use** — TabNexus 不做执行 |
| 一次性、用完即弃的问题 | **Browser Use** — TabNexus 的整理投入不划算 |
| 跨天、跨会话的任务 | **TabNexus** |
| 20+ 页面，需要区分主次和否决项 | **TabNexus** |
| 需要沉淀、复用、交接给他人或其他 Agent | **TabNexus** |
| 企业环境、不能外发正文 | **TabNexus** |

**这张表反过来定义了你的 ICP**：TabNexus 的价值随**任务时长**和**页面数量**增长。一次性 5 个 Tab 的用户不是你的用户，别为他们做产品；**跨天、20+ 页、要出结论的知识工作者**才是。

### 📣 对外话术（可直接用）

> **"Browser Use 让 AI 看见你现在开着的 Tab。
> TabNexus 让 AI 记得这件事从头到尾发生了什么——包括你昨天关掉的那 20 个页面，和你为什么关掉它们。"**
