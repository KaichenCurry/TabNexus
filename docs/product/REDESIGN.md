## 第一部分 · 界面审计（基于空状态截图）

### 1.1 致命发现：这是一张"空状态"截图

请注意一件事——这张截图里 **workspace 里一张卡片都没有**（"0 个分组 · 0"），但屏幕上已经出现了：

**16 个概念 / 控件**：WORKSPACE、我的工作区、0 个分组、? 帮助、分组看板、关系图、添加资料、新建分组、AI 助手、Agent 活动、导出、筛选资料、阅读状态、资料类型、所属分组、显示 0/0、清除筛选……

**右侧另有 12 个**：标签操作台、已选择 0 个、全选、保存 0、本地整理 0、关闭 0、重开 0、"先勾选下方标签"、"当前为本地模式…"、当前窗口、最近关闭·未保存、"全选默认跳过固定标签…"、"1 个浏览器内部页面已隐藏"。

> **一个什么都没有的界面，却需要用户理解 28 个元素。这就是"臃肿"的确切定义。**

对比一下：Linear 的空状态是一句话 + 一个按钮；Notion 的空状态是一个光标。**高级感的第一来源不是配色和圆角，是"该出现的时候才出现"。**

## 第二部分 · 重构方案

### 2.1 第一原则：渐进式呈现（Progressive Disclosure）

> **界面复杂度必须与用户已投入的内容量成正比。**

| 状态 | 应显示 | 应隐藏 |
|---|---|---|
| 0 张卡片 | 一句话输入框 + 收件口 | 筛选栏、关系图、导出、Agent 活动、AI 助手、新建分组、添加资料 |
| 1–5 张 | + 看板 + AI 整理 | 筛选栏、关系图 |
| 6–15 张 | + 筛选、关系图、交给 Agent | — |
| 15+ 张 | + 缺口提示、结论产出 | — |

**这一条单独执行，就能消掉 70% 的臃肿感，且几乎零开发成本（条件渲染）。**

### 2.2 术语统一表（立即执行，改 i18n 即可）

| 现在 | 改为 | 理由 |
|---|---|---|
| 智能整理 / AI 整理 / AI 助手 / 本地整理 | **整理**（一个动词） | 4→1。用不用 AI 是实现细节，不该出现在按钮上 |
| 工作区 Workspace | **任务 Task** | 立住核心对象 |
| 卡片 / 资料 / 来源 | **页 Page** | 呼应"Tab 即文件页" |
| 资料类型（WEB） | **角色**（证据/背景/反例/方案/结论） | 从"哪来的"改成"是什么" |
| 标签操作台 | **收件口 Inbox** | 它是入口，不是操作台 |
| 本地模式 | *（删除）* | 向用户暴露实现细节 |
| 待整理 | 合并进收件口 | 消除第二个暂存区 |
| 已自动保存（常驻） | 改为瞬时 toast | 消除常驻噪音 |

> **工程注意**：「工作区→任务」只改用户界面文案（i18n 即可）；代码标识符与 MCP 17 工具契约（`read_workspace` 等）保持 workspace 不变，避免破坏 189 项测试与既有 Agent 兼容。

```
│  ＋ 新任务 │   └────┘   └────┘   └────┘              │  └──────────┘│
│           │                                          │              │
│ ⚙         │                                          │  已保存 9 ▸  │
└───────────┴──────────────────────────────────────────┴──────────────┘
```

**五处关键改动：**

**① 任务头（P0，ROI 最高）**
主区顶部三行：目标一句话 / 进度条 / 下一步。**这一条把 Workspace 从文件夹变成任务，是整个重构的核心。**
- 目标：首次保存时由 AI 从标题猜一句，用户可改
- 进度：`已读/总数 · N 已采用`
- 下一步：用户手填或 AI 建议
- 右侧一个小圆点显示 MCP 连接状态（`● Codex`）——**让护城河可见**

**② 顶栏收敛 8 → 3**

| 位置 | 内容 |
|---|---|
| 左 | `看板 ｜ 关系图`（视图切换，纯文字 Tab，无边框） |
| 右 | `⋯`（内含：添加资料、新建分组、导出、Agent 活动、设置） |
| 右主 | **`▶ 交给 Agent 继续`**（唯一实心按钮） |

「整理」不放顶栏——它应该在**选中卡片后浮出**的上下文工具条里（选中才有意义）。

**③ 右侧降级为收件口：6 按钮 → 1**
- 只回答一个问题：**当前窗口哪些还没收进来**
- 已保存的默认折叠成 `已保存 9 ▸` 一行
- 「最近关闭」并入折叠区
- 唯一按钮：`收进任务 N`
- 关闭/重开/整理全部移走（属于主区选中态）
- 5 条说明文字 → 0 条（把"固定标签不会被关闭"做成图标 tooltip）

**④ 卡片重设计**

```
现在：  标题                        改为：  ▎证据
        crunchbase.com                     Perplexity 融资轮次
        ●待读 ●浏览器中打开 WEB              "估值 90 亿，未披露 ARR"
                                           crunchbase.com · 已读
```
角色色条上正面，**备注上正面**（最高价值字段），域名降为脚注。

**⑤ 首启：先立事，再收页**

```
                这次你想搞清楚什么？

        ┌────────────────────────────────────┐
        │ 例如：评估 Perplexity 值不值得对标    │
        └────────────────────────────────────┘

              然后从右边把相关的页收进来 →
```

一个输入框，一句提示。**顺带解决了 AI 整理最大的痛点**——现在 AI 整理要用户额外描述意图，很多人不会写；这里在第一秒就自然拿到了。

### 2.4 视觉规范（"简洁高级感"的可执行定义）

| 维度 | 现在 | 改为 |
|---|---|---|
| 强调色 | 紫色用在 6+ 处 | **全局仅 1 处**用主色（主 CTA）；角色色只用于 3px 色条 |
| 卡片层级 | 面板→白卡→按钮卡，三层阴影 | **最多一层**。主区用无边框卡 + 1px 极淡分隔线，去掉阴影 |
| 圆角 | 大圆角 + 大阴影（偏"可爱"） | 8px 圆角，`0 1px 2px rgba(0,0,0,.04)` 或纯边框 |
| 字重 | 大量 14px 常规灰 | 三级：18px/600（任务目标）· 14px/500（卡片标题）· 12px/400 灰（脚注） |
| 留白 | 主区空旷、右侧拥挤 | 统一 8pt 栅格；右侧行高从紧凑改为 44px 单行 |
| 说明文字 | 8 条常驻 | **0 条常驻**，全部转 tooltip 或首启引导 |
| 空状态插画 | 灰色卡片插画 | 删掉，换成输入框 |
| 禁用按钮 | 常驻灰按钮 | **不显示**，选中后才浮出 |

> 一句话：**高级感 = 少一个颜色、少一层阴影、少八条说明。**

## 第三部分 · DSH 插件生态战略

### 3.1 事实核对（2026-08-15）

DeepSeek Harness（dsh）v0.1 开发者预览版于 **2026-08-13** 发布，MIT 开源：

| 项目 | 事实 |
|---|---|
| 仓库 | `github.com/deepseek-ai/deepseek-harness`，npm `@deepseek-ai/dsh` |
| 核心架构 | **Everything is a plugin**，基于 **Cordis** 插件内核（Koishi 生态） |
| 组装模型 | **Bundle**（官方成套配置）→ **Profile**（本机具名清单）→ **Patch**（用户覆盖层），上层覆盖下层 |
| 会话级 | **Preset**（Agent 预设）决定单次会话有哪些工具/提示词/工作流；随附标准 / PTC / 极简 / 创造四种 |
| 生态兼容 | **任何 MCP Server 都可接入**，与内置工具走同一条流水线，同受审批和守卫约束 |
| 现状 | 官方内置 100+ 插件；内测组织 dsh-external 已有 251 个仓库；社区已自建包管理器与 hub 索引 |
| 官方号召 | *"我们期待与全球开发者一起，在开源、开放、可复用、可组合的基础设施之上，共同探索智能上限。欢迎全球 Harness 开发者加入 DSH 插件生态。"* |

**事实核验（可信度说明）**：架构类事实已在本机安装的 `@deepseek-ai/dsh@0.1.0-rc.6` 源码中逐项确认——Cordis 内核、`dsh-mcp-client` 官方描述 *"connects to MCP servers and registers their tools on ctx.tools"*、stdio / Streamable HTTP 双传输、自动重连监督、凭据脱敏，全部属实。生态动态参见：[iThome 公测报道](https://www.ithome.com/0/989/446.htm) · [InfoQ：模型、工具、Agent Loop 全是插件](https://www.infoq.cn/article/de9AljWc4ej2WKAyW8dD) · [36氪深度体验](https://www.36kr.com/p/3938143940820104) · [Oh-My-DSH 社区插件目录](https://github.com/like-study1/Oh-My-DSH)。社区数量（251 仓库 / 545 issue）为第三方统计，引用时以社区实时数据为准。

**关键技术事实**：dsh 跑在本地（默认 `127.0.0.1:3080`，本机实测），**通过浏览器 Web UI 使用**。

> 📌 而你的截图里，右侧收件口第二个标签正是 `127.0.0.1` 的「读取项目文件与 GitHub 项目了解 — DeepS…」。
> **你自己已经在用浏览器开着 DSH 干活了——这不是巧合，这就是场景本身。**

### 3.2 为什么 TabNexus 特别适合做 DSH 插件

这不是蹭热点，是**架构层面的天然契合**，有四条硬理由：

**① dsh 的用户 100% 是重度浏览器用户**
dsh 没有 Electron 客户端，Web UI 就跑在浏览器里。用 dsh 的人，浏览器里同时开着：dsh 自己的 Web UI、GitHub 仓库、文档、Issue、Trajectory 回放……**dsh 用户的标签爆炸问题比普通人更严重**，因为 Agent 还会替他们开页。

**② 你已经有的 17 个 MCP 工具可以零改造接入**
dsh 明确支持任意 MCP Server，且与内置工具同流水线。**TabNexus 现在这套本地 MCP，加一个 bundle 配置就能变成 dsh 插件。**这是你最省力的一步——不是重写，是打包。

**③ dsh 缺一个"跨会话上下文层"，而你正好是**
dsh 有 Trajectory（会话内事件日志）、有上下文压缩、有跨会话检索——但这些都是**关于对话的记忆**。它没有的是**关于任务素材的记忆**：我为这件事看过哪些页、哪些被否决了、结论依据是什么。

> dsh 记得"Agent 说过什么"，TabNexus 记得"这件事参考过什么"。

**④ 你的定位和 dsh 的哲学同构**
dsh 说"一切皆插件"，本质是**把运行时拆成可组合的上下文**；你说"Tab 即文件页"，本质是**把浏览器拆成可组合的任务上下文**。**同一个思想在两个层面的实现。** 这条能让你的口号在 dsh 社区里天然成立。

### 3.3 三层接入方案（按工作量递增）

#### Layer 1 · MCP 直连（1–2 天，立刻可做）

dsh 支持任意 MCP Server。用户在 dsh 配置里加一段就能用：

```yaml
# cordis 配置（多实例：每个 mcp-client 实例连接一个 MCP server）
plugins:
  mcp-client#tabnexus:            # 插件名恒为 mcp-client，#tabnexus 是实例名
    transport: stdio
    serverName: tabnexus          # 必填，[A-Za-z0-9_-]{1,32}；工具名变为 mcp__tabnexus__read_workspace
    command: npx
    args: ['-y', '@tabnexus/mcp']
    env: {}
    cwd: .
    toolCallTimeoutMs: 60000
    failOnStartupError: true      # 首次连接/工具同步失败即加载失败（dsh 约定：配置错误要炸在加载期）
    # reconnect 可省略：默认启用，1s 起指数倍增，10 次上限
```

> ⚠️ 字段以上述 schema 为准（已在本机 `dsh-mcp-client` 源码核验：`serverName`/`command`/`args`/`env`/`cwd`/`toolCallTimeoutMs`/`failOnStartupError` 均为必填，缺失会导致实例加载失败）。配置文件路径以 dsh 官方文档为准。

**产出**：在 README 和 `docs/AGENT_CLIENT_ADAPTERS.md` 里增加 dsh 一行，与 Codex / Cursor / Claude 并列。
**成本**：几乎为零（现有 MCP 已就绪，只需验证 + 写文档）。
**这一步今天就能做，建议立刻做。**

#### Layer 2 · 官方 DSH 插件包（1–2 周，核心动作）

按 Cordis 规范发一个真正的 dsh 插件，而不只是 MCP 配置：

```
@tabnexus/dsh-plugin
├── src/
│   ├── index.ts          # Cordis 插件入口，注册服务
│   ├── service.ts        # 服务定义：TaskContextService（接口规范）
│   ├── provider.ts       # 提供方：连接 Chrome 扩展的本地 broker
│   └── tools.ts          # 消费方：把上下文暴露成 dsh 工具
├── bundle.yml            # 组合包配置
└── README.md
```

**遵守 dsh 的工程约定**（这些是社区认可的门槛，也是质量信号；发布前以 dsh 官方仓库的 CONTRIBUTING 为准）：
- 注册必须是**可逆副作用**（卸载时自动撤销，不留残余）
- 配置错误必须在**加载时报错**，不能静默跳过
- 跨边界标识符用**品牌类型**（branded types）
- 逐文件 100% 单测覆盖、文档与代码同步（dsh 的 CI 门禁标准）

**服务三角色拆分**（dsh 的核心设计，照做能显专业）：
| 角色 | 内容 |
|---|---|
| 服务定义 | `TaskContextService` 接口：读任务、读页、写回结论、更新状态 |
| 提供方 | Chrome 扩展 broker（现有实现） |
| 消费方 | 暴露为 dsh 工具，供模型调用 |

这样**换执行后端只需换提供方**——比如将来支持 Firefox 或 Edge，接口不变。

#### Layer 3 · Agent Preset：「浏览器调研模式」（1 周，差异化亮点）

这是**最有传播力的一步**。dsh 的 Preset 决定一个会话拿到哪些工具和提示词。你可以发一个专用预设：

**`tabnexus-research` 预设**包含：
- TabNexus 上下文工具（读任务、读页、写回）
- 精简的文件工具（写报告）
- 一段专用系统提示词：*"你在协助一个持续多天的调研任务。先读取当前任务上下文，注意已被标记为'已排除'的页——不要重复它们的结论。产出写回 Workspace。"*
- 不含 shell / 危险工具（调研场景不需要，更安全）

**为什么这一步有传播力**：dsh 社区现在的插件多是 TUI 皮肤、emoji、主题这类玩票性质的（据社区披露：大鲸鱼 TUI、上古 QQ 风皮肤、鲸鱼 emoji）。**一个解决真实工作流问题的 Preset，在这个阶段的生态里是稀缺品。**

### 3.4 双形态的关系：不是两个产品，是一体两面

```
        ┌─────────────────────────────────────┐
        │      同一份任务上下文（本地存储）        │
        │   任务 · 页 · 角色 · 备注 · 关系 · 进度  │
        └──────────────┬──────────────────────┘
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
┌────────────────┐          ┌──────────────────┐
│ Chrome 扩展     │          │ DSH 插件          │
│ （人的入口）     │          │ （Agent 的入口）   │
│                │          │                  │
│ 收集 · 整理     │  ←────→  │ 读取 · 补充 · 写回 │
│ 判断 · 查看     │          │                  │
│                │          │ + Research Preset│
│ → Web Store    │          │ → DSH 生态        │
└────────────────┘          └──────────────────┘
```

**关键洞察**：这两个形态**不是渠道的复制，是角色的分工**。
- Chrome 扩展是**人类界面**——人在这里做判断（哪个是证据、哪个被否决）
- DSH 插件是**Agent 界面**——Agent 在这里消费判断并写回产出
- 两者共享同一份本地数据，**互为对方的价值放大器**

这也直接回答了 §POSITIONING 里的 P2：**你不是又一个浏览器 MCP，你是人机之间那份共享上下文的载体。**

### 3.6 DSH 路线的战略价值（为什么值得优先）

| 维度 | Chrome Web Store | DSH 插件生态 |
|---|---|---|
| 竞争密度 | **极高**（Toby/OneTab/Workona/Tabox…数十款） | **极低**（生态 2 天前刚开放，尚无同类） |
| 审核周期 | 数天至数周，政策风险 | 无审核，npm 发布即可用 |
| 用户质量 | 泛化，多为轻度整理需求 | **100% 开发者 + 重度 Agent 用户 = 你的精确 ICP** |
| 与定位契合 | L1 收纳层（你最不想竞争的一层） | **L3 Agent 协作层（你的护城河）** |
| 时间窗口 | 长期存在 | **窗口期极短**——生态早期红利，先发优势显著 |
| 传播 | 靠 SEO 和评分慢慢积累 | 社区活跃（251 仓库/545 issue/单日新增 14），**首批高质量插件天然有曝光** |

> ⚠️ **时间敏感**：dsh 生态 2026-08-13 才开放，现在是第 3 天。这个窗口以周计，不以月计。
> **建议：DSH Layer 1 立刻做（1–2 天），优先级高于任何 UI 改动；Web Store 上架不急。**
