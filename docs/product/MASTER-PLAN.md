## 1. 源码级审计（新增，本次核心增量）

### 1.1 数据模型：缺失的核心字段（🔴 最严重）

`extension/src/core/types.ts` 实际定义：

```ts
export type Workspace = {
  id: string;
  name: string;              // ← 只有一个名字
  createdAt: string;
  updatedAt: string;
  groupOrder: string[];
  groups: Record<string, Group>;
  cards: Record<string, Card>;
  edges: Edge[];
};
```

**这就是"Workspace 退化成文件夹"的硬证据。**

你的全部叙事（"回来就知道为什么打开、做到哪里、下一步是什么"）在数据模型里**一个字段都没有对应**。README 承诺的三件事，代码里全不存在：

| README 承诺 | 数据模型对应 | 状态 |
|---|---|:---:|
| "为什么打开" | 无 | ❌ |
| "做到哪里" | 只有 card 级 status，无任务级进度 | ⚠️ |
| "下一步是什么" | 无 | ❌ |

**必须新增**（向后兼容，全部可选）：

```ts
export type Workspace = {
  // ...现有字段保持不变
  intent?: string;        // 任务目标："评估 Perplexity 的商业模式"
  nextStep?: string;      // 下一步："补一个反面案例"
  conclusion?: string;    // 结论摘要（P3 闭环）
  intentSource?: "user" | "ai";   // 目标是用户写的还是 AI 猜的
  closedAt?: string;      // 任务完成时间（用于度量 P3）
};
```

> ⚠️ 注意 `SCHEMA_VERSION = 1`。新增可选字段不需要升版本，但**建议同时把 storage 的迁移路径测通**，因为 P3 的 `conclusion` 后续可能要扩展成结构化对象。

同时 `Card` 类型的 `type` 字段问题：

```ts
export type CardType = "web" | "note" | "html" | "report" | "agent";
```

这是**来源类型**（这东西是什么格式），不是**角色**（这东西在任务里干什么）。界面上显示的 `WEB` 标签毫无信息量——用户当然知道那是个网页。

**必须新增独立的角色维度**：

```ts
export type CardRole =
  | "background"   // 背景
  | "evidence"     // 证据
  | "counter"      // 反例
  | "option"       // 方案
  | "conclusion"   // 结论
  | "excluded";    // 已排除 ← 关键！负信息

export type Card = {
  // ...现有字段
  role?: CardRole;
  excludedReason?: string;   // 为什么排除（Agent 最需要的负信息）
};
```

> 💡 **`excluded` 这个角色是你对 Browser Use 的核心优势的数据载体**（见 POSITIONING §7.6 第②条）。没有这个字段，"我们记得你否决过什么"就是一句空话。

### 1.2 导出格式：没有任务意图（🔴 严重）

`extension/src/core/export.ts` 实际输出：

```markdown
# TabNexus Workspace: 我的工作区
> 以下内容是按任务意图整理的浏览器上下文，可直接作为 Agent 的任务资料。

## crunchbase.com
- [Perplexity AI — Funding Rounds](https://...)
  - Type: web
  - Source: user
  - Domain: crunchbase.com
```

**问题**：
1. 说是"按任务意图整理"，但**导出内容里根本没有任务意图**——因为数据模型里就没有
2. `Type: web` / `Domain: crunchbase.com` 对 Agent 是**噪音**（URL 里已包含域名信息）
3. 分组名是 `crunchbase.com`——**把域名当任务结构喂给 Agent**
4. 没有进度、没有排除项、没有下一步

**这个导出格式无法支撑你 PRD 里的 H2 假设**（结构化 vs 平铺 URL）。因为它本质上还是"平铺 URL + 域名分类"。

**改造后应为**：

```markdown
# 评估 Perplexity 的商业模式
> 进度：12/18 已读 · 3 已采用 | 下一步：补一个反面案例

## 证据
- [Perplexity AI — Funding Rounds](https://...)
  - 估值 90 亿，但没披露 ARR    ← 用户备注，最高价值
  - 已采用

## 反例
- [Why RAG startups struggle](https://...)
  - 与上面的增长论点矛盾

## 已排除（不要基于这些下结论）    ← Browser Use 永远给不了的部分
- [某篇 2023 年旧测评](https://...)
  - 排除原因：数据过期，产品已重构
```

> 📌 **这个格式改造应该优先于任何 UI 改动**，因为它是 P2（传得走）的实际载体，也是 DSH 插件返回给 Agent 的内容。

### 1.3 域名分组的兜底理由（🟡 反定位）

`extension/src/core/grouping.ts`：

```ts
reason: locale === "zh" ? `与 ${domain} 属于同一网站` : `Shares the ${domain} domain`
```

产品在无 API Key 时，会明确告诉用户"这两个页面在一组，因为它们**来自同一个网站**"。

这与 README 的批判逐字冲突：

> *"按域名整理只能告诉你'页面来自哪里'，却不知道'你为什么打开它'。"*

**默认体验就是自己批判的形态。** 且 `GroupingPolicy` 类型里 `"domain"` 是三个策略之一，说明这是被当作正式方案而非兜底。

**改造**：无 Key 时不做域名分组，改为**生成空的角色骨架**（背景/证据/待定），让用户拖。哪怕手动，也比域名分组更贴合定位。域名分组保留在「更多排序方式」里。

### 1.4 复杂度指标（量化"臃肿"）

| 指标 | 数值 | 评价 |
|---|---:|---|
| 源码行数（extension/src） | **10,143** | 🔴 对一个"标签管理器"而言偏重 |
| `WorkspaceApp.tsx` | **1,316 行** | 🔴 单文件过大，应拆分 |
| `types.ts` | **760 行** | 🔴 类型定义过度设计 |
| `collaboration.ts` | 877 行 | MCP 层，可接受 |
| **i18n 键数** | **736** | 🔴🔴 **这是最强的臃肿信号** |
| 测试用例 | 123（`tests/` 实测） | ✅ 良好 |
| MCP 工具 | 17 | ✅ 足够（不要再加） |
| AI 供应商 | 6 | 🔴 过剩（2 个就够） |

> 📌 数字口径说明：`IMPLEMENTATION_STATUS.md` 记载"189 tests"，实测 `tests/` 目录内 `it(`/`test(` 定义为 123 处（差额应为参数化 `it.each` 展开 + 打包 E2E 场景计数）。建议统一口径，避免对外材料出现两个数字。

> **736 个界面文案键**意味着这个产品试图向用户解释 736 件事。作为对比，一个成熟的中型 SaaS 通常在 200–400。
> **删减 i18n 键数应该作为"简洁度"的量化 KPI：目标砍到 400 以内。**

### 1.5 权限与隐私（✅ 这块做得很好，但没讲出来）

`manifest.json` 实测：

```json
"permissions": ["tabs", "storage", "clipboardWrite"]
```

- ✅ 没有 `<all_urls>`、没有 content script、没有 `webRequest`、没有 `downloads`
- ✅ `incognito: not_allowed`
- ✅ host_permissions 只列了 6 个 AI API 域名 + `file:///*`
- ✅ CSP 严格限制 connect-src，MCP 只允许 `ws://127.0.0.1:43119`

**这是教科书级的最小权限设计**，但在 README 里被写成"合规声明"埋在倒数第三节。

**这应该是竞争武器**：Browser Use / mcp-chrome 类工具需要读取页面全文才能工作；你只读元数据。在企业环境下，**这决定了能不能被批准安装**。

> 建议：把权限对比做成 README 首屏附近的一张表。这是能直接说服 CTO / IT 部门的硬材料。

### 1.6 一个隐藏风险：`file:///*` 权限

manifest 里申请了 `file:///*`（为了支持本地 HTML 卡片）。

⚠️ **Chrome Web Store 审核对 `file:///*` 敏感**，需要在商店描述里明确说明用途，否则可能被要求整改。建议：
- 上架前评估这个权限是否必需
- 若必需，改为**可选权限**（`optional_host_permissions`），用户首次添加本地 HTML 时再请求
- 这同时也是更好的隐私实践

## 2. 定位与三大问题（浓缩版，详见 POSITIONING.md）

### 2.1 核心理念

> **浏览器已成为新操作系统，Tab 已成为新文件页——但浏览器从没给它配文件系统。TabNexus 就是那个文件系统。**

| 文件系统 | 浏览器现状 | TabNexus |
|---|---|---|
| 文件 | Tab（只有 URL） | **Page**（带角色/备注/状态） |
| 文件夹 | 无 | **Task**（一件事的现场） |
| 文件类型 | 网页标题 | **角色**：背景/证据/反例/方案/结论/**已排除** |
| 打开记录 | 历史（时间流） | **进度**：待读/已读/已采用 |
| 引用关系 | 无 | **关系图** |
| 文件系统 API | 无 | **MCP 17 工具 / DSH 插件** |
| 产出文件 | 另存为 | **结论卡片**（写回同一任务） |

### 2.2 三大问题

| | 问题 | 一句话 | 度量 | 战略地位 |
|---|---|---|---|---|
| **P1** | 记不住 | Tab 只存 URL，不存"为什么"，只能靠开着不关当备忘录 | 7 日回访率 ≥40% | 会被平台收编 |
| **P2** | 传不走 | 你在当浏览器和 AI 之间的人肉 API | 周均交给 Agent ≥2 | **护城河** |
| **P3** | 收不拢 | 开 30 个 Tab 是为了一个结论，工具却止步于"存好了" | 产出结论的任务占比 ≥30% | 决定回访率 |

### 2.3 vs Browser Use / mcp-chrome（关键差异）

**必须承认**：读取+总结这件事你没有优势。差异在六条：

**架构上限（他们做不到）**
1. **时间维度** — 他们读 live tabs；三天的调研，第三天只看得到当下 12 个 Tab
2. **负信息** — 你否决过的 8 个页面，他们会平等对待甚至给更高权重
3. **确定性** — 懒加载/登录墙/JS 渲染导致同一问题两次不同答案

**经济性（能做但不划算）**

4. **Token** — 单页正文 5k–50k tokens，30 页爆窗口；你几 k tokens 传完
5. **隐私** — 要总结就要读正文，企业环境直接违规
6. **单向** — 产出流回聊天框就死了；你写回 Workspace，越用越厚

**战略结论**：
> Browser Use 是**感知执行层**，TabNexus 是**记忆判断层**。不是竞品，是上下游。
> 应在文档里明说可配合使用——你不是第 6 个浏览器 MCP，你是它们缺的持久化存储。

## 3. 界面重构（浓缩版，详见 REDESIGN.md）

### 3.1 第一原则：渐进式呈现

> **界面复杂度必须与用户已投入的内容量成正比。**

| 卡片数 | 显示 | 隐藏 |
|---|---|---|
| 0 | 一句话输入框 + 收件口 | 筛选栏、关系图、导出、Agent活动、AI助手、新建分组、添加资料 |
| 1–5 | + 看板 + 整理 | 筛选栏、关系图 |
| 6–15 | + 筛选、关系图、交给 Agent | — |
| 15+ | + 缺口提示、结论产出 | — |

**空状态实测 28 个元素 → 应为 3 个。**

### 3.2 术语统一（改 i18n，2 小时）

| 现在 | 改为 |
|---|---|
| 智能整理 / AI 整理 / AI 助手 / 本地整理（4 个名字） | **整理** |
| 工作区 Workspace | **任务 Task** |
| 卡片 / 资料 / 来源 | **页 Page** |
| 资料类型（WEB） | **角色** |
| 标签操作台 | **收件口** |
| 本地模式 | *删除* |
| 待整理 | 并入收件口 |
| 已自动保存（常驻） | 瞬时 toast |

### 3.3 五处关键改动

1. **任务头**：目标 + 进度条 + 下一步 + MCP 状态点（`● Codex` / `● dsh`）
2. **顶栏 8 → 3**：`看板|关系图` + `⋯` + **`▶ 交给 Agent 继续`**（唯一实心按钮，替换「导出」）
3. **右侧 6 按钮 → 1**：只留 `收进任务 N`；5 条说明 → 0 条
4. **卡片**：角色色条 + **备注上正面** + 域名降脚注
5. **首启**：「这次你想搞清楚什么？」一个输入框

### 3.4 视觉规范（"高级感"的可执行定义）

| 维度 | 规则 |
|---|---|
| 强调色 | **全局仅 1 处**用主色（主 CTA）；角色色只用 3px 色条 |
| 阴影 | **最多一层**；主区改 1px 淡分隔线 |
| 圆角 | 8px（现在偏大显"可爱"） |
| 字重 | 三级：18/600 · 14/500 · 12/400 灰 |
| 说明文字 | **0 条常驻**，全转 tooltip |
| 禁用按钮 | **不显示**，选中后浮出 |

> 高级感 = 少一个颜色、少一层阴影、少八条说明。

## 4. DSH 插件生态战略（最高优先级）

### 4.1 事实（2026-08-13 发布，MIT 开源）

| 项目 | 事实 |
|---|---|
| 仓库 | `github.com/deepseek-ai/deepseek-harness`，npm `@deepseek-ai/dsh` |
| 架构 | Everything is a plugin，基于 **Cordis** 内核 |
| 组装 | **Bundle**（官方成套）→ **Profile**（本机清单）→ **Patch**（用户覆盖），上层覆盖下层 |
| 会话 | **Preset** 决定单次会话的工具/提示词；随附 标准/PTC/极简/创造 |
| 生态 | **支持任意 MCP Server**，与内置工具同流水线、同受审批守卫 |
| 现状 | 官方 100+ 插件；dsh-external 251 仓库；社区已自建包管理器与 hub |
| 运行 | 本地 `127.0.0.1:3080`，**通过浏览器 Web UI 使用** |

> 📌 你的截图右侧第二个标签正是 `127.0.0.1` 的 DeepSeek 页面。**你自己就是目标用户。**

### 4.2 四条契合理由

1. **dsh 用户 100% 是重度浏览器用户** — 无客户端，Web UI 在浏览器里；且 Agent 会替他们开页，标签爆炸更严重
2. **17 个 MCP 工具零改造可接** — dsh 明确支持任意 MCP Server。不是重写，是打包
3. **dsh 缺跨会话素材记忆** — 它有 Trajectory（Agent 说过什么），没有"这件事参考过什么"
4. **哲学同构** — "一切皆插件"是把运行时拆成可组合上下文；"Tab 即文件页"是把浏览器拆成可组合任务上下文

### 4.3 三层接入

#### Layer 1 · MCP 直连（1–2 天）🥇 立刻做

```yaml
# ~/.dsh/cordis.patch.yml
plugins:
  mcp-tabnexus:
    transport: stdio
    command: npx
    args: ['-y', '@tabnexus/mcp']
```

产出：README + `docs/AGENT_CLIENT_ADAPTERS.md` 增加 dsh 一行，与 Codex/Cursor/Claude 并列。

#### Layer 2 · Cordis 插件包（1–2 周）

```
@tabnexus/dsh-plugin
├── src/
│   ├── index.ts      # Cordis 入口
│   ├── service.ts    # 服务定义 TaskContextService
│   ├── provider.ts   # 提供方：Chrome 扩展 broker
│   └── tools.ts      # 消费方：暴露为 dsh 工具
├── bundle.yml
└── README.md
```

**必须遵守 dsh 工程约定**（社区质量门槛）：
- 注册是**可逆副作用**（卸载自动撤销，不留残余）
- 配置错误**加载时报错**，不静默跳过
- 跨边界标识符用**品牌类型**
- 逐文件 100% 单测、文档与代码同步

**服务三角色拆分**（照做显专业）：服务定义 / 提供方 / 消费方独立，将来换 Firefox 只换提供方。

#### Layer 3 · Research Preset（1 周）🌟 最有传播力

`tabnexus-research` 预设：
- TabNexus 上下文工具 + 精简文件工具（写报告）
- 专用提示词：*"你在协助一个持续多天的调研任务。先读取任务上下文，**注意已标记为'已排除'的页，不要基于它们下结论**。产出写回 Workspace。"*
- **不含 shell / 危险工具**（调研场景不需要，更安全）

> 社区现有插件多为 TUI 皮肤、鲸鱼 emoji 等玩票性质。**一个解决真实工作流的 Preset 在早期生态里是稀缺品。**

### 4.4 双形态关系

```
       同一份任务上下文（本地存储）
    任务·页·角色·备注·关系·进度·排除项
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
  Chrome 扩展            DSH 插件
  （人的入口）           （Agent 入口）
  收集·整理·判断  ←──→   读取·补充·写回
   → Web Store          → DSH 生态
```

**不是渠道复制，是角色分工。** 人在扩展里做判断，Agent 在 DSH 里消费判断并写回。

### 4.5 为什么 DSH 优先于 Web Store

| 维度 | Chrome Web Store | DSH 生态 |
|---|---|---|
| 竞争密度 | 极高（数十款） | **极低（第 3 天）** |
| 审核 | 数天–数周，`file:///*` 有风险 | 无审核，npm 发布即用 |
| 用户 | 泛化轻度整理需求 | **100% 开发者 + 重度 Agent 用户 = 精确 ICP** |
| 命中层 | L1 收纳（最卷） | **L3 协作（护城河）** |
| 窗口 | 长期 | **以周计** |

### 4.6 口号

> **「一切皆插件 —— 那浏览器里那 50 个 Tab，也该是。」**
> TabNexus for DSH：把浏览器里散落的任务上下文，变成 Harness 可直接调用的插件化记忆。
> 诚邀全球 Harness 开发者共建 DSH 插件生态。

技术向备选：
> **dsh 记得 Agent 说过什么，TabNexus 记得这件事参考过什么。**

## 附：一页纸

**定位**：浏览器的任务文件系统 — 把 Tab 变成人和 AI 都能接着用的任务上下文

**三问题**：记不住 / 传不走 / 收不拢

**vs Browser Use**：他们读 live tabs 快照，你存跨会话的人类判断。**上下游，非竞品。**

**双形态**：Chrome 扩展（人的入口）+ DSH 插件（Agent 入口），共享同一份本地数据

**最紧急**：DSH Layer 1（1–2 天，窗口以周计）→ intent 字段 + 任务头 → 渐进式呈现

**核心诊断**：功能已过剩，缺的是**一个叫"任务"的一级对象**、**一个叫"已排除"的角色**，和**"该出现时才出现"的克制**。
